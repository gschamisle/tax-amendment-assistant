# 입법예고 의견 군집화·요약

국민참여입법센터에 달린 입법예고 의견을 **같은 취지끼리 묶어 건수 순으로 정렬**하고,
상위 X개 군집의 주요내용을 보고서로 뽑는 파이프라인이다. 종합부동산세법처럼 1,600건이
넘게 달리는 입법예고에서 "여론이 어디에 몰렸는가"를 한 장으로 보기 위한 도구다.

```
[수집]  scripts/fetch_opinions.py   ─► data/opinions/{bill}.json
[정규화] core/opinion_normalize.py
[군집화] core/opinion_cluster.py
[태깅]  core/opinion_tagging.py
[요약]  core/opinion_summary.py     (상위 X개 군집만 · Claude)
[출력]  scripts/analyze_opinions.py ─► output/opinions-{bill}.md + CSV 2종
```

## 설계 원칙 — 통계는 결정적으로, 문장만 LLM으로

저장소 제1원칙과 같다. **몇 건이 같은 말을 했는가는 규칙·유사도가 정하고, LLM은 이미
확정된 군집을 사람이 읽을 문장으로 옮기기만 한다.** 그래서:

- 실행할 때마다 군집·건수가 달라지지 않는다(입력 순서를 바꿔도 동일 — 테스트로 고정)
- `--no-llm`으로 API 키 없이도 같은 구조의 리포트가 나온다
- 요약이 틀려도 건수·비율·조문 분포는 흔들리지 않는다

난수를 쓰지 않고, 파이썬 내장 `hash()`(프로세스마다 시드가 다름) 대신 `zlib.crc32`를
쓰는 것도 같은 이유다.

## 1. 수집 (`core/opinion_source.py`)

### 두 경로

| 경로 | 언제 | 진입점 |
|------|------|--------|
| HTTP 크롤링 | 평소 | `fetch_opinions(bill_id, …)` |
| 파일 폴백 | 사이트 개편·접근 차단·수기 저장 | `load_from_files([...])` |

두 경로 모두 같은 `OpinionRecord`를 만들고, 이후 단계는 출처를 구분하지 않는다.

### 세는 단위 — 행이 아니라 의견 (2026-08-07 실측)

사이트는 의견 1건을 **그 의견이 지정한 개정항목마다 한 행씩** 렌더링한다.
1페이지 20행이 고유 의견 8건이었고, 한 의견이 13행을 차지한 사례가 있다.
따라서 목록 상단의 `입법의견건수`는 의견 수가 아니라 **(의견 × 대상항목) 행 수**다.

| 층위 | 종부세법(87936) 실측 |
|------|-----:|
| `입법의견건수` 표시 = 행 수 | 1,828 |
| 공개 의견 행 (`opnOpYn=A`는 로그인 필요) | 약 1,497 |
| **고유 의견** | **840** |

행 단위로 세면 한 사람 의견이 열세 번 집계되고, 그냥 접으면 어느 개정항목에 달린
의견인지가 사라진다. `dedupe_records()`는 **접되 대상 개정항목을 `title`에 합친다**
(`merge_title`, 구분자 `TITLE_SEP`).

### 증분 수집 (접수기간 중 반복 실행)

```bash
uv run python scripts/fetch_opinions.py --bill 87936 --append
```

목록이 최신순이라 새 의견은 앞 페이지에 쌓인다. `--append`는 기존 `data/opinions/{bill}.json`을
`known`으로 깔고 시작해, **아는 의견만 나오는 페이지에 닿으면 멈춘다** — 그 뒤는 전부 아는
것이기 때문이다. 실측: 전량 76페이지 → 증분 2페이지(새 의견 1건). 새 의견이 없으면 1페이지에서
멈추므로 매일 돌려도 부담이 없다.

### 수집 정확도의 한계

DOM에 안정적인 의견 ID가 없어 `_synthetic_id()`가 **제출시각(분) + 본문 전체**로 대체
식별자를 만든다. 두 실패 사이의 타협이다.

- 날짜만·본문 일부로 만들면 → 같은 날 같은 문구를 낸 **서로 다른 사람이 1건으로 접힌다**
- 페이지 내 위치를 넣으면 → 마감일에 새 의견이 유입돼 목록이 밀릴 때 **같은 의견이
  다시 잡혀 13배로 부풀었다**(실측)

남는 한계: **같은 분에 같은 문구**를 낸 서로 다른 제출은 한 건으로 접힌다. 목록이 최신순
고정이고 정렬 파라미터가 없어(확인함) 실시간 유입 중 완전 정확한 크롤은 불가능하다.
집계는 하한선으로 읽어야 한다.

### 사이트 구조가 바뀌면

파싱은 XPath 설정 기반이다. 고치는 순서:

```bash
# 1) 1페이지 원문 HTML을 받아 둔다
uv run python scripts/fetch_opinions.py --bill 87936 --probe
#    → data/opinions/_probe/87936-page1.html

# 2) 그 HTML에서 의견 1건을 감싸는 요소를 찾아 XPath를 적는다
cat > data/opinion-selectors.json <<'JSON'
{
  "row":        "//ul[@class='opn-list']/li",
  "opinion_id": ".//@data-opn-id",
  "title":      ".//p[@class='tit']//text()",
  "body":       ".//div[@class='cont']//text()",
  "author":     ".//span[@class='name']//text()",
  "posted_at":  ".//span[@class='date']//text()",
  "stance":     ".//span[@class='agree']//text()"
}
JSON

# 3) 다시 수집
uv run python scripts/fetch_opinions.py --bill 87936 --pages 3   # 소량으로 먼저 확인
```

설정 XPath가 0건을 물어오면 `parse_generic_html()`이 받아낸다. 반복 블록 후보
(`//table//tbody/tr`, `//ul/li` 등)마다 "3건 이상 · 본문이 충분히 길고 · 날짜가 절반
이상 보이는" 정도로 점수를 매겨 가장 그럴듯한 집합을 고른다. 응답이 JSON이면
`parse_json_payload()`가 `opnCn`/`의견내용` 같은 흔한 키 이름을 알아서 매핑한다.

### 페이지네이션 안전장치

페이지 파라미터명(`--page-param`, 기본 `pageIndex`)이 사이트와 맞지 않으면 매 페이지가
같은 내용을 돌려준다. **새 의견이 하나도 없으면 즉시 멈춘다** — 같은 페이지를 수백 번
긁는 사고를 막기 위한 것으로, 중단 사유가 그대로 출력된다.

### 개인정보·예의

- 작성자 실명은 **저장하지 않는다.** 수집 시점에 `홍길동 → 홍*동`으로 마스킹하고,
  동일 작성자 판별용으로는 복원 불가능한 해시(`author_hash`)만 남긴다.
  (`test_opinion_source.py`가 어떤 필드로도 실명이 새지 않는지 검사한다)
- 기본 요청 간격 1초(`--delay`), 식별 가능한 User-Agent, 페이지 상한(`--pages`)
- robots.txt를 확인하고 금지 경로면 수집을 중단한다(`--no-robots`로 생략 가능)
- 수집 원문은 `data/opinions/`(gitignore)에만 둔다. 저장소에 올리지 않는다.

## 2. 정규화 (`core/opinion_normalize.py`)

| 처리 | 이유 |
|------|------|
| NFKC · 소문자 · HTML 태그 제거 | 표기 차이 제거 |
| 3회 이상 반복 문자 축약 | `!!!!!`, `ㅠㅠㅠ` 잡음 제거 |
| 한글·숫자·영문·`%`만 유지 | `%`는 세법 의견에서 그 자체가 주장(`60%로 인하`) |
| 세법 약칭 통일 | `종부세 → 종합부동산세`, `1가구1주택 → 1세대1주택` |
| 상투구 제거 | 인사말이 같다고 다른 의견이 묶이는 것을 방지 |
| 공백 제거 후 문자 3-gram | 조사 변형·띄어쓰기 흔들림에 강함(형태소 분석기 불필요) |

### 상투구 제거의 안전장치

복붙 의견이 코퍼스의 절반을 차지하는 게 정상이라, "자주 나오는 문장"을 그냥 지우면
**정작 핵심 주장이 사라진다.** 그래서 두 겹으로 막는다:

1. 실질 신호(조문 인용·숫자·`폐지/인하/과세` 등 주장 어휘)가 있는 문장은 df가 아무리
   높아도 상투구로 보지 않는다
2. 제거 결과가 빈 문자열이면 원문을 그대로 돌려준다

curated 인사말 패턴(`안녕하십니까`, `감사합니다`, `적극 검토를 부탁드립니다` …)은 df와
무관하게 항상 제거 대상이다. `--no-boilerplate-strip`으로 이 단계를 끌 수 있다.

## 3. 군집화 (`core/opinion_cluster.py`)

### 3단 구조

| 단계 | 방법 | 기본 임계값 |
|------|------|------------|
| ① 완전 중복 | 정규화 텍스트 해시 | — |
| ② 근사 중복 | MinHash(64 perm) + LSH(16밴드) → Jaccard 검증 | `--dup-threshold` 0.80 |
| ③ 유사 의견 | 문자 3-gram TF-IDF 코사인, 희귀 n-gram 역색인 블로킹 | `--threshold` 0.45 |

세 단계의 간선을 union-find로 이어 연결요소를 군집으로 삼는다.

**①이 먼저인 것이 성능의 핵심이다.** 복붙 의견을 하나의 "변형"으로 접고 나면 이후
단계가 다루는 N이 크게 줄어든다(실측: 2,000건 → 고유 42종 → 0.08초). IDF도 변형 기준으로
센다 — 복붙 800건을 800으로 세면 그 문구의 idf가 0에 수렴해 정작 가장 큰 덩어리를
구분하지 못한다.

### 과병합 방지 (적응형 재분할)

유사도 그래프는 체이닝으로 서로 다른 취지를 한 덩어리로 붙일 수 있다. 그래서
**전체의 35%를 넘으면서 응집도가 0.55 미만인 군집만** 임계값을 0.1 올려 재분할한다
(최대 2회). 응집도 조건이 있어서, 진짜로 큰 단일 쟁점 군집(예: "종부세 폐지" 800건)은
쪼개지지 않는다.

### 임계값 조정

`--dump-pairs N`으로 임계값 경계(±0.1) 부근 쌍을 표본 출력해 눈으로 보정한다.

```bash
uv run python scripts/analyze_opinions.py --bill 87936 --no-llm --dump-pairs 20
```

- 서로 다른 취지가 한 군집에 섞이면 → `--threshold`를 올린다
- 같은 말인데 군집이 갈라지면 → 내린다. 그래도 안 붙으면 표현 차이가 큰 경우이므로
  `ABBREVIATIONS`(약칭 사전)에 표면형을 추가하는 편이 낫다

**실측(합성 1,670건 · 정답 테마 11종 기준):** 임계값 0.35~0.50에서 군집 결과가 사실상
같고 취지 혼입이 0건이다. 0.30으로 내리면 혼입이 생기기 시작한다. 즉 **임계값을 내려도
"표현이 완전히 다른 같은 주장"은 붙지 않고 순도만 나빠진다** — 이 간극은 임계값이 아니라
아래의 쟁점별 합계로 메운다.

### 성능 실측

| 코퍼스 | 시간 |
|--------|------|
| 2,000건 / 고유 42종 (복붙 다수 — 실제 입법예고에 가까움) | 0.08초 |
| 1,600건 / 전부 고유 (최악 가정) | 약 5초 |
| 5,000건 / 전부 고유 (최악 가정) | 약 38초 |

전부 고유한 경우가 최악이고, 이때 후보쌍 수가 빠르게 늘어 대략 제곱으로 증가한다.
수만 건 규모에서 느리면 `TOP_TERMS_PER_DOC`(역색인에 넣을 term 수)을 줄이면 되지만,
재현율이 함께 떨어지므로 `--dump-pairs`로 확인하고 조정한다.

## 4. 태깅 (`core/opinion_tagging.py`)

- **관련 조문** — `core/citation_parser.py`를 그대로 재사용한다. `제7조`,
  `「소득세법」 제12조`, 범위 인용(`제7조부터 제9조까지`)까지 기존 파서가 처리하고,
  법령명이 생략된 인용은 `--law`로 준 대상 법률로 해석한다. 군집별로 집계하면
  "어느 조문에 의견이 몰렸는가"가 바로 나온다.
- **찬반** — 찬성/반대 어휘 + 조건부 표지(`다만`, `취지에는 공감`). 판단이 안 서면 `불명`.
  `폐지` 요구는 반대 의견으로 읽는다.
- **요구사항** — 폐지·철회 / 완화·인하 / 강화·인상 / 유지·존치 / 개선·보완.
  찬반보다 실무에 직접 쓰인다.
- **쟁점 태그** — `ISSUE_LEXICON`(1세대 1주택, 공정시장가액비율, 세부담 상한, 합산배제 …).
  다른 세목을 분석할 때는 이 사전에 항목을 추가한다.

## 5. 요약 (`core/opinion_summary.py`)

상위 X개 군집에 대해서만 Claude를 호출한다(**호출 수 = 군집 수**, 기본 20). 입력은
대표의견 + 표본 최대 5건 + 키워드 + 규칙기반 추정치이고, 출력은 JSON 스키마로 강제한
`{쟁점명, 주요내용, 요구사항[], 스탠스, 대표인용, 관련조문[]}`이다.
모델 폴백은 `core/llm_review.py`의 `structured_call()`을 재사용한다.

군집 구성 해시를 키로 `data/opinions/{bill}-summary.json`에 캐시하므로, 군집이 그대로면
재실행은 무과금이다. 한 군집의 요약이 실패해도 나머지 리포트는 완성되고, 실패한 군집은
결정적 라벨(대표의견 첫 문장 + 키워드)로 표시된다.

## 6. 산출물

| 파일 | 내용 |
|------|------|
| `output/opinions-{bill}.md` | 총계 → 전체 분포 → **쟁점별 합계** → 상위 X개 군집 요약표 → 군집별 주요내용 → 롱테일 |
| `output/opinions-{bill}-clusters.csv` | 군집 요약표 (순위·건수·비율·쟁점명·스탠스·조문·키워드·응집도) |
| `output/opinions-{bill}-members.csv` | **전 건**의 군집 배정 — 군집 판정이 타당한지 사람이 감사하는 표 |

리포트 숫자를 믿으려면 `members.csv`에서 표본을 뽑아 확인하는 절차를 권한다. 군집이
잘못 묶였다면 임계값 조정이나 약칭 사전 보강으로 대응한다.

### 쟁점별 합계 — 군집 순위와 함께 봐야 하는 표

군집은 표면형 기준이라, 같은 주장을 완전히 다른 말로 쓴 의견은 별개 군집으로 갈린다
(실측: 1주택 폐지 요구 400건이 5개 군집으로 분산). 건수 순 상위 목록만 보면 같은 주제가
여러 번 나와 **주제의 실제 규모를 놓친다.** 그래서 쟁점 태그 기준 집계를 함께 낸다
(위 실측에서 `1세대 1주택` 406건으로 복원 — 정답 400건).

한 의견이 여러 쟁점을 담으면 각 쟁점에 모두 세므로 합계는 총 의견수를 넘는다. 군집마다
대표 쟁점을 하나만 고르는 방식도 시도했으나, `1세대 1주택`과 `이중과세`처럼 동점일 때
선택이 자의적이 되어 오히려 주제를 쪼갰다.

> **쟁점 사전을 늘릴 때 주의:** 한국어는 어절 경계가 없어 짧은 표면형이 다른 단어 속에
> 그대로 들어간다. 실제로 `중과`가 **이**중과세에 부분일치해 305건이 오태깅된 적이 있다.
> 앞뒤가 붙어도 뜻이 유지되는 형태(`중과세율`, `중과 유지`)만 쓰고, 사전을 고치면
> `test_opinion_cluster.py`의 부분일치 회귀 테스트에 사례를 추가한다.

## 한계

- **의미가 아니라 표면형 유사도다.** 표현이 완전히 다른 같은 주장(예: "세금이 너무 많다"
  ↔ "조세부담률이 과도하다")은 갈라질 수 있다. 약칭 사전·쟁점 사전이 이 간극을 일부
  메우지만 완전하지 않다. 임베딩 기반 백엔드는 재현성을 이유로 채택하지 않았다.
- **찬반 규칙은 반어·비꼼을 못 읽는다.** 상위 군집의 스탠스는 Claude 요약이 보정하지만,
  롱테일은 규칙 결과 그대로다.
- **사이트 구조 의존.** 국민참여입법센터가 개편되면 셀렉터를 다시 잡아야 한다
  (`--probe` → `data/opinion-selectors.json`).
- **한 의견은 한 군집에만 속한다.** 여러 쟁점을 함께 담은 긴 의견은 가장 가까운 한 곳에만
  잡히므로, 조문별 분포는 군집이 아니라 의견 단위 집계(`article_distribution`)를 본다.

## 테스트

```bash
uv run python -m scripts.test_opinion_source    # 파싱·마스킹·폴백
uv run python -m scripts.test_opinion_cluster   # 군집 purity·중복접기·결정성·리포트
uv run python -m scripts.run_offline_tests      # 전체 (위 2개 포함)
```

픽스처는 `data/opinion-fixtures/`의 **합성 데이터**다. 실제 사이트 HTML은 개인이 작성한
글이므로 저장소에 넣지 않는다.

### 실제 규모로 시험·보정하기

`scripts/make_demo_opinions.py`가 실제 분포 특성(복붙 캠페인·표현 변형·인사말·롱테일)을
흉내낸 합성 코퍼스를 만든다. **`테마` 열이 정답 라벨**이라 군집 결과와 대조해 순도를
실측할 수 있다 — 위 임계값 표와 성능 수치가 이걸로 나왔다.

```bash
uv run python scripts/make_demo_opinions.py                    # 1,670건
uv run python scripts/make_demo_opinions.py --scale 3          # 5,000건 (성능 시험)
uv run python scripts/analyze_opinions.py --bill DEMO --law 종합부동산세법 \
    --top 12 --no-llm --from-files output/demo-opinions.csv
```

임계값이나 사전(`ISSUE_LEXICON`·`ABBREVIATIONS`)을 바꾼 뒤에는 이걸로 순도가 나빠지지
않았는지 확인하고 나서 실제 데이터에 적용한다.

> ⚠️ 생성물은 합성 데이터다. 리포트 숫자를 정책 근거로 인용해서는 안 된다.
